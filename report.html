vLLM Load Test Report — Token Throughput and Cost

Overview — What We Measured and How We Got the Break-Even Point

The main chart is Required Throughput vs Cost (Break-Even). For a given monthly token demand, it shows which is cheaper: running your own GPUs on EC2, or paying Bedrock per token. The throughput tables and curves below it are the measurements that chart is built from.

1. The two cost structures

  • Self-hosted (EC2 + vLLM): charged per hour. You pay for instances × hours whether you use them or not, so cost per token drops as demand grows. One instance can only handle so much, and past that you add another instance, so the cost goes up in steps.
  • Bedrock (Claude Haiku 4.5 / GPT-5.6 Luna): charged per token. Cost is proportional to demand, so it is a straight line. Idle time costs nothing.

So the two lines cross somewhere: Bedrock is cheaper at low demand, EC2 is cheaper at high demand. To find where they cross, we need one measured number: how many tokens per second one EC2 instance can handle without falling behind.

2. Method: raise the request rate until the server falls behind

Model: Qwen/Qwen3.5-4B (text-only, prefix caching enabled). Load tool: vllm bench serve. We raise the request rate in steps (Poisson arrivals) instead of fixing concurrency.

vLLM 0.25.1, served with:

vllm serve Qwen/Qwen3.5-4B --language-model-only --reasoning-parser qwen3 --enable-prefix-caching

--language-model-only skips the vision encoder and frees its memory for KV cache. --enable-prefix-caching is off by default and is required, since the cache-ratio axis means nothing without it. On g7.2xlarge only, --max-model-len 65536 was added because the default 262,144 does not fit in 32GB alongside the weights. On p5.4xlarge the startup log reports bfloat16, gpu_memory_utilization 0.92, max_num_batched_tokens 8,192, and a KV cache of 60.61 GiB (1,960,086 tokens).

Each measurement is one client run:

vllm bench serve --model Qwen/Qwen3.5-4B --dataset-name random --random-input-len <input − prefix> --random-output-len <output> --random-prefix-len <input × cache ratio> --request-rate <rps> --num-prompts <max(10, rate × 60)> --seed <per-run> --ignore-eos

--random-prefix-len is how the cache ratio is applied: that many tokens are shared by every request. --ignore-eos forces the full output length. The seed is unique per run, because with the default seed 0 the previous run's prompts stay in the prefix cache and inflate the effective cache ratio.

  1. Pick a workload shape (input tokens × output tokens × cache ratio).
  2. Raise the offered rate: 0.1 → 0.5 → 1 → 2 → 5 → 10 → 20 → 50 → 100 req/s.
  3. Record measured throughput and TTFT at each rate.
  4. Saturation rule: when measured req/s < offered rate × 0.8, the server is not keeping up (the queue is growing and latency is climbing), so we stop.

3. Why we use the rate just before saturation

Throughput at saturation is a higher number, but at that point the queue backs up and TTFT gets too long to use. So we take the throughput at one rate step before saturation as what one instance can actually handle. This means the break-even numbers assume latency stays usable.

4. What we measured

  • Input tokens: 1,000 / 5,000 / 10,000 / 50,000 (shown as line style in the charts)
  • Output tokens: 100 / 500 / 1,000 / 2,000 (dropdown)
  • Cache ratio: 10% / 50% / 80%, set as the shared-prefix fraction. This stands for how much of the prompt (such as a system prompt) is reused. The charts are split by this.
  • Instances: p5.4xlarge / g7e.2xlarge / g7.2xlarge, same test on each

That is 48 shapes per instance type (4 inputs × 4 outputs × 3 cache ratios). The 1,000-token input and 100-token output rows were added after the first run to cover a light per-request front stage; they sit below the original 5,000-token input and 500-token output floors.

5. How we turn throughput into cost

Self-hosted per month = ceil(required TPM ÷ (stable tokens/s × 60)) × EC2 hourly rate × 730h
Bedrock per month = required TPM × 60 × 730h ÷ 1,000,000 × $/1M tokens

The EC2 hourly rate can be set to On-Demand, Savings Plans, or Capacity Blocks with the dropdown.

The Bedrock $/1M is a blended rate worked out per request, then divided by total tokens:

$ per request = (input × cache ratio × cache-read price + input × (1 − cache ratio) × input price + output × output price) ÷ 1,000,000
$/1M tokens = $ per request ÷ (input + output) × 1,000,000

So at cache 80%, 80% of the input is billed at the cache-read price and 20% at the normal input price. Cache reads cost a tenth of normal input for both models: Haiku 4.5 is $0.10 vs $1.00 per 1M, Luna is $0.022 vs $0.22 per 1M. That is why the Bedrock lines drop as the cache ratio goes from 10% to 80%.

Cache writes (Haiku $1.25, Luna $0.275 per 1M) are left out. A prefix is written once and then read by many requests, so the write is small next to the reads. Note this makes the Bedrock figures the optimistic end at high cache ratios: if a prefix were rewritten on every request, the cost at cache 80% would be roughly twice what is shown. Prices are US Geo CRIS.

6. What this does not cover

  • Infrastructure cost only. It does not say the models are equal in quality (Qwen3.5-4B vs Haiku 4.5 vs Luna).
  • EC2 numbers assume the instance runs at the stable operating point 24/7. If your real utilization is lower, your cost per token is higher.
  • Operational work, availability design, redundancy, and scaling are not included.
  • Bedrock throughput quotas are not included.
